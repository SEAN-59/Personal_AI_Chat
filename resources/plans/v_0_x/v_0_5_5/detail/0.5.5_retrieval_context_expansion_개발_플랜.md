# v0.5.5 검색 컨텍스트 확장 개발 플랜

- Milestone: v0.5.5: Retrieval Context Expansion
- Issue: #91 feat: Expand retrieval context for complete table answers
- Branch: `feature/91-expand-retrieval-context`
- Base: `develop`

---

## 1. 요약 (Summary)

표/목록형 질문(예: "경조사에서 지급하는 모든 종류 알려줘", "모든 종류 다 알려줘")에서 retriever가 상위 청크 몇 개만 잘라 들고 오면서, 같은 문서 내 표의 나머지 행이 누락되어 LLM이 부분 답변을 내는 회귀를 잡는다. 핵심은 **인접(neighbor) 청크 확장** — 한 문서에서 hit이 발생하면, 같은 document의 연속된 chunk_index 범위를 안전한 budget 내에서 추가로 컨텍스트에 끼워 넣는다. 청킹 알고리즘은 건드리지 않고 retrieval/prompt 조립 단계만 보강한다. v0.5.4의 query_rewriter monetary guard는 그대로 두고, follow-up/ordinal/monetary 회귀가 깨지지 않도록 회귀 테스트로 봉인한다.

## 2. 현재 증상 (Current Symptoms)

- "경조사에서 지급하는 모든 종류 알려줘" → 표의 일부 행만 답변에 등장. 사실상 전체 종류 enumeration이 필요한 질문인데도 일부가 누락.
- "모든 종류 다 알려줘" 류의 광범위 enumeration → top-K 청크에 표 머리/일부 행만 들어가서 답이 잘림.
- 후속 질문 "비싼거?", "2번째로 비싼거?" → v0.5.4 monetary guard로 retrieval은 안정화됐지만, 같은 표의 모든 행이 컨텍스트에 들어와야 ordinal 비교가 정확해진다. v0.5.5 목표는 "표 전체 컨텍스트"이므로, monetary/ordinal/comparative 질문도 표/목록 marker가 함께 발견되면 expansion을 허용해 같은 표를 통째로 끌어와야 한다. 단, `비싼거`처럼 정보가 너무 짧고 table marker도 없는 follow-up은 미발동으로 둔다.

## 3. 원인 분석 (Root-Cause)

실제 코드 기준 병목 매핑:

1. **Retriever top-pool 자체는 충분 — final top-K가 작다.**
   - `files/services/retriever.py`: `VECTOR_POOL_SIZE=20`, `KEYWORD_POOL_SIZE=20`. 후보 풀은 넓지만 RRF 병합 후 `top_k` 만큼 잘린다.
   - `chat/services/single_shot/retrieval.py`: `CHUNK_CANDIDATES=10` → `CHUNK_TOP_K=5`. 표가 3~6개 청크에 걸쳐 있으면 일부만 prompt에 들어간다.
2. **Reranker가 의미 다양성을 우선 → 표 연속 청크가 분산된다.**
   - `chat/services/reranker.py`: LLM이 "관련 있는 순서" 라벨만 매기므로, 같은 표의 인접 청크들 중 일부만 상위에 남고 나머지가 떨어진다.
3. **Prompt 조립이 인접성을 모른다.**
   - `chat/services/prompt_builder._render_user_content`의 실제 동작: `chunk_hits` 리스트의 full chunk content를 받은 순서대로 append 한다. 명시적인 `자료 N` 라벨은 **핵심 발췌(`_extract_key_excerpts`) 섹션에만** 존재하고, full chunk 본문 자체에는 자료 번호 헤더가 붙지 않는다 (chunk 사이 구분자만 있음). `DocumentChunk.chunk_index`는 `ChunkHit.chunk_index`로 흘러오지만 prompt 측에서 활용하지 않는다.
4. **표/목록 enumeration 질문 신호가 query 단에서 사라진다.**
   - `query_rewriter`는 "모든", "전부", "전체" 같은 enumeration 단서를 그대로 통과시키지만, retrieval 단계에서 이 신호로 청크 윈도우를 넓히는 경로가 없다.

결론: **bottleneck은 final top-K 컷오프 + 같은 문서 인접 청크 미수집**. 1차 후보 풀을 더 넓히는 게 아니라, hit 청크 주변의 **document-local neighbor expansion**으로 같은 표를 통째로 끌어오는 게 가장 작은 변경으로 가장 큰 효과를 낸다.

## 4. 구현 설계 (Scope)

### 4.1 Neighbor expansion in retrieval

위치: `chat/services/single_shot/retrieval.py` (신규 헬퍼 또는 retrieve_documents 내부 후처리).

설계:
- `retrieve_documents(question)`이 reranker top-K를 받은 직후, 각 hit의 `(document_id, chunk_index)`를 기준으로 같은 document 내 인접 청크를 추가 조회한다.
- 윈도우 정책:
  - 기본 윈도우 반경 `NEIGHBOR_RADIUS = 2` (앞/뒤 각 2개) → 표 한 개를 통째로 덮기 충분.
  - 같은 document에서 여러 hit이 인접하면 윈도우를 **병합** (예: hit chunk_index 4, 6 + radius 2 → 2~8 한 범위로 묶기).
  - 같은 document에 hit이 너무 많이 몰려도 윈도우 상한 `MAX_NEIGHBOR_CHUNKS_PER_DOC = 8`.
- 적용 조건 (보수적으로):
  - (필수) reranker가 반환한 hit이 있다 (= 검색 결과 자체가 비어있지 않다).
  - 그리고 아래 셋 중 하나를 만족해야 발동:
    1. **Enumeration 의도가 명시적으로 있다.** 질문이 enumeration 단서(`모든`/`전부`/`전체`/`종류`/`목록`/`리스트`/`다 알려줘`/`전부 다`) 중 하나를 포함하면 발동 후보. 단, `항목` 단어는 enumeration trigger에서 **제외**한다 — v0.5.4 query_rewriter가 `비싼거?`를 `경조사 지급금액 중 가장 큰 항목` 같은 monetary rewrite로 만들 때 우연히 trigger되는 것을 피하기 위함. 또는
    2. **같은 document hit ≥ 2개 AND 해당 hit 청크 내용에 표/목록 marker가 보인다.** marker는 chunk content에 markdown table 구분자(`|`가 한 줄에 2개 이상 + 다음 줄에 `---`), 또는 연속 목록 마커(라인 시작이 `-`/`*`/`1.`/`①` 등) 3줄 이상을 보수적으로 판정. enumeration intent도 표 marker도 없으면 단순히 같은 문서 hit이 두 개라는 이유만으로는 발동하지 않는다. 또는
    3. **Monetary/ordinal/comparative query + 명시적 표 metric + 표/목록 marker.** monetary/ordinal/comparative marker(`비싼`/`싼`/`큰`/`작은`/`높은`/`낮은`/`많은`/`적은`/`최대`/`최소`/`가장`/`제일`/`첫 번째`/`두 번째`/`N번째`/`지급금액 기준` 등)가 query에 있더라도, query가 **명시적 금액/표 metric 어휘**(예: `금액`/`지급금액`/`지급액`/`비용`/`기준`)를 포함하고 **해당 hit 청크에 표/목록 marker가 보이면** expansion을 허용한다 — 0.5.5 목표인 "표 전체 컨텍스트 확보"를 위해, 표 기반 비교 질문은 같은 표를 통째로 끌어와야 ordinal 비교가 안정된다. 단, query가 너무 짧고(예: `비싼거?`, `2번째로 비싼거?`) 명시적 metric 어휘도, table marker 검출도 없으면 monetary/ordinal-only로 간주해 expansion을 **skip** 한다.
  - 위 조건 어디에도 해당하지 않으면 v0.5.4 동작 그대로 (회귀 0).
  - 보충 (단위 테스트(6.1)에 명시적으로 추가):
    - `휴가 며칠 쓸 수 있어?` 같은 비-표 일반 질문은 같은 document hit이 2개 이상이라도 표/목록 marker가 없으면 미발동.
    - `비싼거?` 단독 follow-up(짧은 monetary/ordinal-only, table marker 미검출) → 미발동.
    - `경조사 지급금액 중 가장 큰 항목` + table marker 있음 → 발동(조건 3).
    - `경조사 지급금액 중 가장 큰 항목` + table/list marker 없음 → 미발동.
    - `항목` 단어 단독 포함 query → enumeration trigger로 간주하지 않음(미발동).
- 데이터 조회: `DocumentChunk.objects.filter(document_id=did, chunk_index__in=range(...)).select_related('document')` 한 번에 묶어 조회. status=READY 필터는 retriever와 일관성 유지.
- 결과 조립 (표/목록 순서 보존):
  - hit을 **document 단위로 그룹화**한다. document 그룹의 **상대 순서**는 그 document에서 처음 등장한 원본 hit의 reranker 순위로 결정.
  - 각 document 그룹 **내부**에서는 원본 hit + 확장 neighbor 청크를 모두 합쳐 **document-local `chunk_index` 오름차순**으로 정렬한다. 이렇게 해야 표가 chunk 4~8에 걸쳐 있고 원본 hit이 chunk 6일 때도 prompt에 4 → 5 → 6 → 7 → 8 순서로 들어가 표/목록 순서가 깨지지 않는다.
  - 중복 chunk_id는 제거 (set 기반).
  - 회귀 테스트(6.1)에 “원본 hit이 chunk 6, neighbor 4·5·7·8 → 최종 hit 리스트가 4·5·6·7·8 순서” 케이스를 추가한다.
- Budget cap:
  - 전역 상한 `MAX_TOTAL_CHUNKS_AFTER_EXPANSION = 12` (기본 top-K 5 + 확장 최대 7).
  - 문자 길이 기반 budget `MAX_EXPANSION_CHARS = 8000`자. **기준은 “추가된 neighbor 청크만”이 아니라 “최종 expanded hits 전체 content length의 합”**으로 계산한다 (원본 hit 청크가 이미 길어 prompt가 부풀어 오르는 것을 방지). 누적 합이 cap을 넘으면 그 시점부터 neighbor 청크를 더 부착하지 않는다 — 원본 hit은 절대 잘리지 않으며, 잘리는 건 추가 neighbor 청크 뿐. 원본 hit만으로 이미 cap을 초과하더라도 안전하게 expansion을 skip 한다.
  - 테스트(6.1)도 이 “최종 전체 합 기준” 정의에 맞춰 작성한다.
- 반환 타입: 기존 `List[ChunkHit]` 유지. 추가 부착된 인접 청크는 `score=0.0`(혹은 원본 hit의 score 값 미만으로 표시)으로 채워 sources에 인용 가능하게 한다.

상수는 `chat/services/single_shot/retrieval.py` 모듈 상단에 명명 상수로 선언. 수치는 본 플랜에서 강제 값으로 박지 않고 구현 PR에서 실측(테스트로 조정) — 단, 위 디폴트가 시작점.

### 4.2 Prompt 조립에서 인접 청크 표기

위치: `chat/services/prompt_builder._render_user_content`.

- **현재 구조 정정**: full chunk 본문에는 `자료 N` 라벨이 없고, 핵심 발췌 섹션에만 `자료 N` 라벨이 붙는다. 따라서 “자료 N 메타를 단순 prepend”로 해결할 수 있는 구조가 아니다.
- **이번 phase 결정**: prompt 조립 변경은 **보류**한다. retrieval 단의 neighbor expansion + document-local chunk_index 정렬(4.1)만으로 표 순서가 보장되므로, prompt_builder는 기존 동작을 유지한다. 자료 라벨/헤더 신설은 별도 phase에서 다룬다.
- `_extract_key_excerpts`(v0.5.3 핵심 발췌)도 이번 phase에서는 **변경 없음**. prompt_builder를 손대지 않는 이상 neighbor 청크 여부를 prompt 단에서 식별할 수 없으므로, 발췌 정책 분기는 불가능하다. neighbor 청크의 발췌 노이즈 제어는 prompt_builder 개편과 함께 후속 phase 후보로만 남긴다.
- 즉 이번 phase에서 `chat/services/prompt_builder.py`는 **전혀 변경하지 않는다**. `test_prompt_builder.py`도 추가/수정 없음.

### 4.3 Drift 방지 가드 (unrelated 청크 끌려오기 방지)

- Neighbor expansion은 **이미 hit이 발생한 document에 한정**. 새 document를 끌어오지 않는다.
- 같은 document 내 hit chunk와 chunk_index 거리 > `NEIGHBOR_RADIUS` 인 청크는 제외.
- 후속 질문이 ordinal/monetary/comparative 비교(`비싼거`, `2번째`, `가장 큰`)인 경우는 §4.1 조건 3(monetary/ordinal + 명시적 표 metric + table marker)을 만족할 때에 한해 expansion이 발동한다. 짧은 monetary/ordinal-only follow-up(예: `비싼거?`)이고 명시적 metric 어휘·table marker가 모두 없으면 미발동이다.
- 같은 document 내 hit이 1개인데 enumeration 단서도 없으면 expansion 미발동.

### 4.4 follow-up / ordinal / monetary 회귀 방지

- `chat/services/query_rewriter.py`의 monetary metric guard, prompt(`assets/prompts/chat/query_rewriter.md`)는 본 PR에서 손대지 않는다.
- 회귀 테스트 추가:
  - `비싼거` follow-up: rewrite 결과에 `지급금액 기준`이 여전히 부착되어 query_rewriter 출력은 유지되고, expansion 발동 여부는 §4.1 조건 3에 따른다(table marker 유무에 의해 결정).
  - "모든 종류" enumeration 질문은 expansion 발동, "비싼거" 단독 follow-up(table marker 미검출)은 미발동, `경조사 지급금액 중 가장 큰 항목` + table marker 존재 시 발동(§4.1 조건 3), 동일 query에서 table/list marker가 없으면 미발동임을 단위 테스트로 박는다.
- expansion 결과 sources에 들어가는 추가 청크는 `build_sources`(`chat/services/single_shot/postprocess.py`)가 그대로 인용 가능해야 한다 — `ChunkHit` 인터페이스를 깨지 않고 chunk_id/document_id/document_name/document_url/content/chunk_index가 채워져 있어야 한다.

### 4.5 Agent retrieve tool 경로 & table_lookup workflow 경로

**Agent path는 이번 phase에서 out-of-scope.** `chat/services/agent/tools_builtin.py::_summarize_retrieve` 가 `hits[:_RETRIEVE_TOP_N]`(현재 3)만 보여주고 각 hit도 400자 window로 잘라 observation summary를 만든다. retrieve_documents 호출 자체는 같지만, neighbor 청크가 원본 hit 뒤가 아니라 document-local chunk_index 순서로 섞여 들어가더라도 agent observation에는 상위 3개 chunk 일부만 노출되어 “자동 적용된 것처럼 보이지 않을” 수 있다. 따라서:
- 본 phase에서는 `_summarize_retrieve`의 top-N/window 정책을 변경하지 않는다.
- 9장의 “Agent path 자동 적용” 표현은 삭제하고, agent path 동작은 v0.5.4와 사실상 동일하게 유지됨을 명시한다.
- agent path의 observation summary 정책(top-N/window/순서)을 retrieval expansion에 맞춰 손보는 작업은 별도 phase에서 다룬다. smoke 테스트는 “agent path가 깨지지 않음” 수준만 확인.

**`chat/workflows/domains/general/table_lookup.py` 도 `retrieve_documents` 를 직접 호출**한다. neighbor expansion이 무조건 적용되면 table candidate 수가 늘어 `_MAX_TABLES_IN_PROMPT=6` 트리밍 동작이 바뀔 수 있다. 결정:
- `retrieve_documents` 에 **`expand_neighbors: bool` 옵션(기본값 `True`)** 을 추가한다.
- `chat/services/single_shot/__init__.py`(또는 single_shot 호출 경로)에서는 기본값(`True`)으로 호출 → single_shot은 expansion 적용.
- `chat/workflows/domains/general/table_lookup.py`는 명시적으로 `expand_neighbors=False`로 호출 → 이번 phase에서는 table_lookup workflow 동작이 v0.5.4와 동일하게 유지된다. 이유: table_lookup은 자체 candidate pruning(`_MAX_TABLES_IN_PROMPT`)이 있어 expansion이 candidate 산정 방식과 이중 작용할 위험이 있다.
- agent path(`chat/services/agent/tools_builtin.py::_retrieve_callable`)는 이번 phase에서 out-of-scope를 유지하기 위해 `retrieve_documents(query, expand_neighbors=False)`로 **명시 호출**한다. 그러면 `_summarize_retrieve`와 `_retrieve_failure_check`가 보는 hits가 v0.5.4와 동일하게 유지된다. agent path에 expansion을 적용하는 작업은 별도 phase에서 `_summarize_retrieve` top-N/window 정책과 함께 다룬다.
- 테스트: 
  - `expand_neighbors=True` (default) — 단위 테스트(6.1)에서 검증.
  - `expand_neighbors=False` — “table_lookup 경로가 호출하는 형태로 expansion이 발동하지 않음” 케이스 추가.
  - **`chat/tests/test_workflow_table_lookup.py`** (필수): table_lookup workflow가 `retrieve_documents(query, expand_neighbors=False)` 형태로 호출하는지 호출 계약을 검증한다 (mock으로 retrieve_documents call args 검증). 이번 phase에서 `chat/workflows/domains/general/table_lookup.py`를 실제로 수정하므로 회귀 봉인 필수.

### 4.6 BO 파일관리 청크 확인/재임베딩과의 관계

- v0.5.3에서 도입된 청크 확인 UI는 `DocumentChunk` 모델 그대로를 조회하므로 schema 변경이 없어 영향 없음. neighbor expansion은 검색 시점 후처리이므로 BO data layer와 무관.

## 9. 핵심 설계 결정 (Key Decisions)

- **Document-local neighbor expansion만 한다.** retriever pool을 키우거나 reranker top-K를 키우는 대신, 이미 hit한 document 안에서 chunk_index 윈도우로 확장 — 회사 자료 사이의 false-positive 끌어오기를 구조적으로 차단.
- **Generic enumeration 단서 단어**만 사용 (`모든`/`전부`/`종류` 등). 도메인 어휘(경조사/조부모 등) 하드코딩 금지.
- **v0.5.4 query_rewriter 경로는 변경 없음.** monetary guard, prompt 모두 그대로. 회귀는 테스트로 봉인.
- **Budget cap 3중**: 문서당 윈도우 상한 + 전체 청크 상한 + 누적 문자 상한. context blow-up 방지.
- **Prompt 조립 변경은 최소화**: 현재 full chunk 본문 단순 나열 구조 유지(full chunk 본문에는 자료 N 라벨이 없음). 1차 PR에서는 retrieval 단의 청크 추가만으로 효과 검증.
- **schema 변경 없음**: `DocumentChunk.chunk_index`/`document_id`만 사용. migration zero.
- **Agent path는 out-of-scope**: `_summarize_retrieve`의 top-N/window가 그대로라 자동 적용으로 보기 어렵다. observation summary 정책 변경은 별도 phase로.
- **`retrieve_documents`에 `expand_neighbors` flag 추가**: single_shot은 `True`(default), table_lookup workflow와 agent path(`_retrieve_callable`)는 `False`로 명시 호출해 이번 phase에서는 expansion 영향 범위를 single_shot으로 한정한다.

## 11. Manual QA 후속 보강 (2026-05-18)

**증상**: '경조사에서 지급하는 모든 종류 알려줘' 질문이 rerank 이전 단계에서 복리후생 chunk 5~7을 후보로 잡지 못함. 개인정보/괴롭힘/결재라인 등 무관 chunk 가 keyword 검색에 들어옴.

**원인**: `files/services/retriever.py::_extract_keywords` 가 토큰 끝의 조사·어미를 제거하지 않아 '경조사에서', '지급하는' 이 그대로 ILIKE 키워드로 들어가고, '모든'/'종류' 같은 generic enumeration 단서는 stopword 가 아니라서 false-positive 를 끌어옴.

**대응**:
- generic 한국어 접미사 화이트리스트(`_TOKEN_SUFFIXES`) 한 번 strip — 도메인 어휘 하드코딩 없음.
- `_STOPWORDS` 에 '모든/전부/전체/종류/목록/리스트/말해줘/보여줘' 등 enumeration·질문 보조어 추가.
- 결과: `_extract_keywords('경조사에서 지급하는 모든 종류 알려줘')` → `['경조사', '지급']`.
- 회귀 테스트: `files/tests.py` 에 `ExtractKeywordsNormalizationTests`, `SearchChunksKeywordNormalizationRegressionTests` 추가.
