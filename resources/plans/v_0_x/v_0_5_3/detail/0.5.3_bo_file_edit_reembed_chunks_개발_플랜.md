# v0.5.3 BO 파일관리: 검토 완료 문서 수정 + 재임베딩 + 청크 확인 개발 플랜

- Milestone: v0.5.3: BO File Edit & Re-embed
- Branch: `feature/<이슈번호>-bo-file-edit-reembed-chunks` (이슈 번호 확정 후 `resources/git-flow.md` 규칙에 따라 생성)
- Base: `develop`

---

## 0. TL;DR

READY 상태 문서도 BO 파일관리에서 텍스트 수정 후 재임베딩할 수 있게 한다. 파일 목록에 "청크 확인" 버튼(read-only 페이지)과 "수정" 버튼을 추가한다. 재임베딩 실패 시 기존 READY 문서의 `edited_text`, `chunks`, `status` 를 **완전히 보존**하여 검색 서비스가 중단되지 않도록 한다.

---

## 1. 배경 / 목표

현재 BO 파일관리(`bo/views/files.py`)에서:
- REVIEWING / FAILED 문서만 `review` 페이지로 이동할 수 있다 (`files.html` L75 조건).
- READY 문서는 텍스트 수정 수단이 없다.
- 저장된 `DocumentChunk` 를 BO 화면에서 볼 방법이 없다.

운영 중에 문서 내용 오류를 발견하거나 텍스트 후처리가 필요할 때 READY 문서를 재수정해야 하는 요구가 생겼다.

---

## 2. In Scope

1. 파일 목록 액션 열 버튼 순서 재배치: **청크 확인** | **수정** | **삭제**
2. READY 문서 수정 가능: `review` 뷰가 REVIEWING/FAILED 뿐만 아니라 READY 상태도 진입 허용.
3. READY 문서 수정 제출 시 프론트 confirm 경고 ("재임베딩이 실행됩니다").
4. 수정 제출 시 안전 재임베딩: 새 청크 + 임베딩 성공 후 트랜잭션에서 원자 교체. 실패 시 기존 상태 완전 보존.
5. `pipeline.py` 에 READY 재수정 전용 헬퍼 `reembed_document(doc, new_text)` 추가 (기존 `finalize_document` 와 경로 분리).
6. 청크 확인 페이지: `DocumentChunk` 를 `chunk_index` 순으로 read-only 표시 (모달 금지, 수정 금지).
7. `bo/views/files.py` 의 `confirm` 뷰 분기: REVIEWING/FAILED → 기존 `finalize_document` 경로, READY → `reembed_document` 경로.
8. `bo/urls.py` 에 청크 확인 URL 추가.
9. 자동 테스트: 버튼 노출/순서, READY 재임베딩 성공/실패 안전 보존, chunk 확인 페이지 read-only.
10. 수동 QA 시나리오.

---

## 3. Out of Scope

- 청크 수동 편집 기능.
- 청크 확인 페이지 모달 방식 (요구사항: 별도 페이지).
- 일괄(batch) 재임베딩.
- REVIEWING → READY 최초 확정 흐름 변경 (기존 `finalize_document` 그대로 유지).
- BO 인증/권한 도입 (기존 BO 패턴 유지).
- `retriever.py` 의 Document.status 필터 추가 (현재 설계 범위 아님, §5 리스크 참조).

## 4. 핵심 안전 계약

### 4.1 현재 `finalize_document` 의 문제점 (READY 재수정에 그대로 쓰면 안 되는 이유)

`files/services/pipeline.py` L94–107:
```python
with transaction.atomic():
    DocumentChunk.objects.filter(document=document).delete()   # 기존 청크 선삭제
    DocumentChunk.objects.bulk_create([...])                   # 새 청크 저장
    document.status = Document.Status.READY
    document.save(...)
```

- **문제**: `document.status = PROCESSING` (L77) 는 `transaction.atomic()` 밖에서 먼저 실행됨.
- READY 문서가 `reembed_document` 진입 시 곧바로 PROCESSING 상태가 됨.
- `embed_texts()` (외부 API) 호출이 실패하면 `_mark_failed()` 가 호출되어 **READY 문서가 FAILED 로 전락**하고 검색 서비스가 중단됨.
- 기존 `finalize_document` 는 REVIEWING/FAILED → READY 최초 확정 경로용으로 설계되었으므로 READY 재수정에 재사용하면 위 문제가 발생함.

### 4.2 READY 재수정 안전 계약 (반드시 준수)

| 단계 | 행동 | 금지 사항 |
|---|---|---|
| 재임베딩 시작 전 | 기존 `edited_text`, `status=READY`, 기존 `chunks` 그대로 유지 | status 변경 금지 |
| 새 청크/벡터 생성 | 메모리에서만 진행 | DB 에 선삭제/선저장 금지 |
| 새 임베딩 성공 시 | `transaction.atomic()` 안에서 한 번에: `edited_text` 교체 + 기존 chunks 삭제 + 새 chunks `bulk_create` + `status=READY` + `error_message=''` | 트랜잭션 밖 부분 저장 금지 |
| 실패 시 | 기존 `edited_text`, `chunks`, `status=READY` 전부 그대로. `error_message` 만 갱신 | `_mark_failed()` 호출 금지 (status FAILED 전환 금지) |

### 4.3 경로 분리 계약

| 시나리오 | 함수 | 실패 시 status |
|---|---|---|
| REVIEWING/FAILED → 최초 확정 | `finalize_document(doc)` (기존, 변경 없음) | FAILED (기존 동작 그대로) |
| READY → 재수정 | `reembed_document(doc, new_text)` (신규) | READY 유지 (검색 계속 가능) |

**`confirm` 뷰 분기 로직**:
```
if doc.status == Document.Status.READY:
    reembed_document(doc, edited_text)  # 실패해도 READY 유지
else:
    doc.edited_text = edited_text; doc.save(...)
    finalize_document(doc)              # 기존 경로
```

### 4.4 `retriever.py` stale chunk 리스크 (§6 에도 명시)

`files/services/retriever.py` 의 `search_chunks()` 는 `Document.status` 를 필터하지 않고 `DocumentChunk` 전체를 검색한다. READY 재임베딩 실패 시 기존 chunks 가 남아있으므로 검색은 계속 동작한다 → **안전 계약 4.2 를 지키는 한** stale chunk 문제는 발생하지 않는다. (기존 chunks 를 삭제하지 않으므로 `edited_text`/chunks 불일치가 생기지 않음.)

## 6. 구현 단계

### 단계 1 — `files/services/pipeline.py`: `reembed_document` 신규 추가

- **기존 `finalize_document` 는 변경하지 않는다.**
- `reembed_document(doc: Document, new_text: str) -> int` 신규 함수:
  1. `new_text.strip()` 빈값이면 `PipelineError` 발생 (status 변경 없음).
  2. `chunks = chunk_text(new_text)` 메모리에서만 실행.
  3. `vectors = embed_texts(chunks)` 메모리에서만 실행.
  4. 성공 시:
     ```python
     with transaction.atomic():
         DocumentChunk.objects.filter(document=doc).delete()
         DocumentChunk.objects.bulk_create([...])
         doc.edited_text = new_text
         doc.status = Document.Status.READY
         doc.error_message = ''
         doc.save(update_fields=['edited_text', 'status', 'error_message'])
     ```
  5. 실패 시 (`EmbeddingError`, `PipelineError`, 기타 `Exception`):
     - **`_mark_failed()` 호출 금지** (status READY 유지).
     - `doc.error_message = str(e)[:2000]` 만 저장:
       ```python
       doc.error_message = str(e)[:2000]
       doc.save(update_fields=['error_message'])
       ```
     - `raise PipelineError(str(e)) from e` 로 뷰에 전달.
  6. `return len(chunks)`.

- `__all__` 또는 import 에 `reembed_document` 추가.

### 단계 2 — `bo/views/files.py`: `confirm` 뷰 분기 + `chunks` 뷰 신규

#### `confirm` 분기

```python
from files.services.pipeline import PipelineError, extract_document, finalize_document, reembed_document

@require_POST
def confirm(request, pk):
    doc = get_object_or_404(Document, pk=pk)
    edited = (request.POST.get('edited_text') or '').strip()
    if not edited:
        messages.error(request, '편집된 텍스트가 비어있습니다.')
        return redirect('bo:review', pk=pk)

    try:
        if doc.status == Document.Status.READY:
            chunk_count = reembed_document(doc, edited)
        else:
            doc.edited_text = edited
            doc.save(update_fields=['edited_text'])
            chunk_count = finalize_document(doc)
    except PipelineError as e:
        messages.error(request, f'임베딩 실패: {e}')
        return redirect('bo:review', pk=pk)

    messages.success(request, f'"{doc.original_name}" 처리 완료 (청크 {chunk_count}개)')
    return redirect('bo:files')
```

#### `chunks` 뷰 신규

```python
def chunks(request, pk):
    """저장된 DocumentChunk 를 chunk_index 순으로 read-only 표시."""
    doc = get_object_or_404(Document, pk=pk)
    chunk_list = doc.chunks.order_by('chunk_index')  # related_name="chunks" (files/models.py)
    context = {
        'doc': doc,
        'chunks': chunk_list,
        'total': chunk_list.count(),
    }
    return render(request, 'bo/files_chunks.html', context)
```

현재 뷰 자체는 상태 제한이 없으므로 변경 불필요. 다만 READY 문서 진입 시 template 에서 안내 문구/버튼 레이블을 분기한다 (§7).

### 단계 5 — `bo/templates/bo/files_review.html`: READY 수정 시 경고 confirm + 취소 버튼 분기 + error_message 노출

현재 "임베딩 진행" 버튼은 단순 form submit (`<form method="post" action="{% url 'bo:confirm' doc.pk %}">`).

변경:
- READY 문서일 때 form `onsubmit` 에 `confirm()` 추가:
  ```html
  <form method="post" action="{% url 'bo:confirm' doc.pk %}"
        {% if doc.status == 'ready' %}
        onsubmit="return confirm('이미 검색 가능한 문서입니다. 수정을 진행하면 임베딩을 새롭게 실행합니다. 계속하시겠습니까?');"
        {% endif %}>
  ```
- 상태 별 버튼 레이블:
  - REVIEWING/FAILED: "임베딩 진행" (기존)
  - READY: "재임베딩 진행"
- READY 상태 안내 배너 추가:
  ```
  이 문서는 이미 검색 가능한 상태입니다. 텍스트를 수정하고 제출하면 기존 청크를 교체하여 재임베딩합니다.
  ```

#### 취소 버튼 분기 계약 (READY vs REVIEWING/FAILED)

현재 좌측 하단에는 `취소 및 삭제` 버튼과 `업로드를 취소하고 파일을 삭제하시겠습니까?` confirm 문구가 있다. READY 문서에서 "수정" 경로로 이 페이지에 진입하면 해당 문구가 오조작을 유발한다.

**계약**: `doc.status == 'ready'` 일 때는 `취소 및 삭제` 버튼을 노출하지 않는다. 대신 좌측 하단에 `← 목록으로` 링크(`bo:files`)를 표시한다. 삭제 기능 자체가 필요하다면 레이블을 `문서 삭제`, confirm 문구를 `이미 검색 가능한 문서를 삭제합니다. 계속하시겠습니까?`로 명확히 변경해야 한다. (v0.5.3 기본 구현은 `← 목록으로` 링크 방식을 권장.)

```html
{% if doc.status == 'ready' %}
  <a href="{% url 'bo:files' %}" class="btn btn-sm">← 목록으로</a>
{% else %}
  {# 기존 취소 및 삭제 버튼 유지 #}
  <button ... onclick="return confirm('업로드를 취소하고 파일을 삭제하시겠습니까?')">취소 및 삭제</button>
{% endif %}
```

#### error_message 노출 계약

재임베딩 실패 시 `doc.error_message` 는 DB 에 저장되지만 `messages.error()` flash 는 1회성이라 새로고침 후 사라진다. review 페이지 상단에 저장된 `doc.error_message` 를 직접 렌더링하여 실패 원인이 영속적으로 보이도록 한다:

```html
{% if doc.error_message %}
  <div class="alert alert-danger" role="alert">
    <strong>마지막 임베딩 오류:</strong> {{ doc.error_message }}
  </div>
{% endif %}
```

이 블록은 READY / REVIEWING / FAILED 모든 상태에서 `error_message` 가 있으면 표시한다.

### 단계 6 — `bo/templates/bo/files_chunks.html`: 청크 확인 페이지 신규

- 별도 페이지 (모달 금지).
- read-only, 수정 입력 없음.
- `chunk_index` 순 표시.
- 각 청크에 번호(`#N`), 글자수, 내용 표시.
- 상단 문서 정보: `original_name`, `status`, 총 청크 수.
- 뒤로가기: "← 파일 목록" 링크 (`bo:files`).
- 템플릿 구성 예시:
  ```html
  {% extends 'bo/base.html' %}
  {% block title %}청크 확인 — {{ doc.original_name }}{% endblock %}
  {% block content %}
  <header class="page-header">
    <h1 class="page-title">청크 확인</h1>
    <p class="page-description">{{ doc.original_name }} · 총 {{ total }}개 청크</p>
  </header>
  <a href="{% url 'bo:files' %}" class="btn btn-sm">← 파일 목록</a>
  {% for chunk in chunks %}
    <section class="card" style="margin-top: var(--space-4);">
      <h3 class="card-title">#{{ chunk.chunk_index }} <small>({{ chunk.content|length }}자)</small></h3>
      <pre style="white-space: pre-wrap; word-break: break-word;">{{ chunk.content }}</pre>
    </section>
  {% empty %}
    <div class="empty-state">청크가 없습니다.</div>
  {% endfor %}
  {% endblock %}
  ```

#### 9.1.1 버튼 노출 및 순서

- READY 문서: `청크 확인` 버튼 노출, `수정` 버튼 노출, `삭제` 버튼 노출.

```python
# 예시 케이스 — 전역 find 대신 해당 문서 행 HTML 범위만 검사하여 다른 행/문구에 의한 오통과 방지
def test_ready_doc_shows_all_three_buttons_in_order(self):
    doc = Document.objects.create(..., status='ready')
    response = self.client.get(reverse('bo:files'))
    content = response.content.decode()
    # 해당 문서 pk 가 포함된 행 블록만 잘라낸다
    row_start = content.find(f'bo/files/{doc.pk}/')
    row_end = content.find('</tr>', row_start)
    row_html = content[row_start:row_end]
    chunk_pos = row_html.find('청크 확인')
    edit_pos = row_html.find('수정')
    delete_pos = row_html.find('삭제')
    self.assertGreater(chunk_pos, -1, '청크 확인 버튼 없음')
    self.assertLess(chunk_pos, edit_pos)
    self.assertLess(edit_pos, delete_pos)
```

## 10-A. QA 발견 보강 (v0.5.3 supplement)

> 이 절은 v0.5.3 QA 중 발견된 `InputNormalizationRule` contains 규칙의 over-apply 버그 수정을 기록한다.

### 발견 사항

- `contains` 규칙 `경조 → 경조사` 가 이미 `경조사` 를 포함하는 입력에 재적용되어 `경조사사`, `경조사사 알려줘` 를 생성함.
- `조부모상` 같은 도메인/띄어쓰기 보정은 Python 하드코딩 없이 BO exact 규칙으로 등록해야 한다.

### 수정 방향

- **contains self-expansion guard 정밀화**: `chat/services/input_normalizer.py` contains 분기에서 `rule.pattern in canonicalize(rule.replacement)` 인 경우, 각 occurrence 위치를 개별 검사해 이미 canonical replacement 의 시작인 위치는 건너뛰고 그 외 첫 번째 위치에서만 치환. 전체 규칙을 건너뛰는 broad guard 에서 occurrence-level 판별로 세분화.
- `조부모상 → 조부모 상` 은 BO `exact` 규칙으로 등록 (Python 하드코딩 없음).

### 영향 케이스 (테스트 보강)

| 입력 | 규칙 | 기대 결과 |
|---|---|---|
| `경조사` | contains `경조→경조사` | unchanged (guard 적용) |
| `경조사 알려줘` | contains `경조→경조사` | unchanged (guard 적용) |
| `경조 한도` | contains `경조→경조사` | `경조사 한도` (정상 치환) |
| `경조사와 경조 한도` | contains `경조→경조사` | `경조사와 경조사 한도` (앞 canonical 건너뛰고 뒤 shorthand 치환) |
| `조부모상` | exact `조부모상→조부모 상` | `조부모 상` |

## 10-B. QA 보강 S2 — 최종 답변 prompt history sanitization

> v0.5.3 BO 재임베딩 QA 중 발견된 **이전 assistant 답변에 의한 numeric 오염** 회귀를 기록한다.

### 발견 사항

- BO 에서 파일을 재임베딩한 결과 `Document.edited_text` 와 `DocumentChunk.content` 에는 `조부모 상 2000만` 이 정확히 반영되어 있다.
- 같은 세션에서 이전 assistant 답변이 `조부모 상은 200만 원입니다` 로 누적되어 있는 상태에서 다시 `조부모 상` 을 물으면, retrieval top hit (chunk 630, `조부모 상\n2000만\n2일`) 가 명확함에도 최종 답변 LLM 이 이전 assistant history 의 `200만` 에 끌려 잘못 답하는 사례가 ChatLog 160~163 에서 관찰되었다.

### 원인

- `chat/services/prompt_builder.py` 의 `build_messages` 가 `messages.extend(history)` 로 이전 assistant 답변을 그대로 LLM 입력에 포함시키고 있었다.
- 답변 LLM 입장에서 본인의 과거 답변은 권위 있는 사실로 인식되어, 같은 turn 의 회사 자료보다 우선하는 현상.

### 수정 방향 (Claude 구현 / Codex 검토)

1. `build_messages` 가 답변 생성용 history 를 `_sanitize_history_for_answer` 로 정제한다. 정책: **assistant role 메시지는 모두 제외하고 user role 만 유지**. 대화 흐름은 보존되되, 옛 답변의 숫자/금액/일수가 모델 입력에 들어가지 않는다.
2. `query_rewriter` / `llm_router` / `workflow_input_extractor` 가 쓰는 history 는 **건드리지 않는다**. 이 보강은 최종 single-shot 답변 prompt_builder 계층만 대상으로 한다.
3. `assets/prompts/chat/source_instruction.md` 에 한 줄 보강: *이전 대화 히스토리·이전 assistant 답변과 현재 회사 자료가 충돌하면 현재 회사 자료를 따르고, 이전 답변의 숫자·금액·일수는 근거로 재사용하지 말 것*.

### 테스트 (chat/tests/test_prompt_builder.py `BuildMessagesHistorySanitizationTests`)

| 테스트 | 단언 |
|---|---|

## 10-C. QA 보강 S3 — 핵심 발췌 prompt + ChatLog dedup stale answer 차단

> S2 보강 이후에도 같은 세션 재임베딩 시 ① 회사 자료 전체를 그대로 나열만 하면 모델이 핵심 수치를 흘리고, ② 유사도 dedup 이 너무 공격적이라 stale ChatLog 에 새 피드백이 붙는 회귀가 추가로 관찰되었다.

### 발견 사항

- BO 입력 정규화 rule id=4 `조부모상 → 조부모 상` 활성화, 서버 로그에서도 normalized 가 찍힘.
- retrieval top hit (DocumentChunk 630) 의 content 안에 `2000만` 이 있음.
- 그럼에도 새 세션 호출 응답은 `200만` 으로 잘못 생성.
- 같은 응답에 매핑된 ChatLog 는 신규 row 가 아니라 기존 ChatLog 163 (답변 `200만`) 이 재사용됨 → 피드백이 stale log 에 박힘.

### 원인

- `chat/services/prompt_builder.py`: chunk content 를 통째로 dump 만 하고 핵심 매치 위치를 강조하지 않아 LLM 이 다른 인접 수치에 끌리는 사례.
- `chat/services/qa_retriever.py` `save_chat_log`: 유사도 ≥ 0.90 이면 answer/sources 차이를 무시하고 무조건 기존 ChatLog 반환.

### 수정 방향 (Claude 구현 / Codex 검토)

1. `prompt_builder._extract_key_excerpts` 신설. query source 는 `search_query` 우선, 없으면 `question`. phrase → 길이 ≥2 token 순으로 chunk content 안 첫 매치 위치를 찾아 ±150자 window (최대 320자) 발췌. `_render_user_content` 가 발췌가 있을 때 `[자료 N 핵심 발췌]` 라벨로 회사 자료 본문 **앞**에 노출.
2. `assets/prompts/chat/source_instruction.md` 에 한 줄 보강: 핵심 발췌 블록이 있으면 그 수치/금액/일수를 최우선으로 인용.
3. `qa_retriever.save_chat_log`: 유사 existing 이 있어도 `answer != ` 또는 `sources != ` 면 새 ChatLog 생성. 둘 다 같을 때만 기존 재사용 (피드백 응집은 유지).

### 테스트

| 테스트 | 단언 |
|---|---|
| `BuildMessagesHistorySanitizationTests.test_key_excerpt_section_precedes_full_chunks` | `[자료 1 핵심 발췌]` 라벨이 `=== 회사 자료 ===` 보다 먼저 나오고, 라벨 아래 블록에 `2000만` / `조부모 상` 포함 |
| `…test_key_excerpt_prefers_search_query_over_raw` | `search_query='조부모 상'`, raw=`'비싼거'` 일 때 핵심 발췌가 `조부모 상` 기준으로 잡힘 |
| `…test_key_excerpt_section_absent_when_no_match` | 질문과 chunk 가 겹치지 않으면 핵심 발췌 블록이 안 나옴 |
| `SaveChatLogDedupTests.test_reuses_existing_when_answer_and_sources_match` | 유사 + answer/sources 동일 → 기존 재사용 |
| `…test_creates_new_when_answer_differs` | 유사하지만 answer 가 다르면 새 ChatLog 생성 |
| `…test_creates_new_when_sources_differ` | sources 가 다르면 새 ChatLog 생성 |

### 영향 / 회귀

- query_rewriter / llm_router / workflow extractor / retriever 경로 변화 없음.
- 기존 prompt_builder S2 / search_query 테스트 그대로 통과.
- ChatLog dedup 정책 변경으로 동일 질문/동일 답변 케이스는 기존과 동일하게 단일 row 유지, 답변 변경 시에만 row 추가.
