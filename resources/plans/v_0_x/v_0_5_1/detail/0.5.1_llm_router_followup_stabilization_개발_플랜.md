# v0.5.1 LLM Router Follow-up Stabilization 개발 플랜

- Issue: #83 fix: Stabilize LLM router follow-up handling
- Milestone: v0.5.1: LLM Router Stabilization
- Branch: `fix/83-llm-router-stabilization`

## 1. 목표
v0.5.0 릴리스 전, LLM Router(`question_router`) + Query Rewriter(`query_rewriter`) 의 후속질문(follow-up) 처리 안정화. 회귀 테스트로 fragile case 를 고정한다.

## 2. In Scope
- 회귀 테스트 보강 중심. 필요 시 prompt/룰 최소 수정.
- Fragile case 별 기대 계약은 §3 표 참조.

## 3. Fragile Cases — 기대 계약
LLM tier 그룹은 follow-up 으로서 `single_shot` + `query_rewriter` 경로가 살아 있어야 하고, DATE_CONDITION 그룹은 tier 우선순위상 LLM Router 보다 먼저 agent 로 라우팅되며 `_llm_classify` 는 호출되지 않아야 한다.

**Single_shot vs agent 분리 기준** (llm_router prompt 가이드라인으로 박제):
- `single_shot`: 이전 대화의 같은 문서/표를 다시 조회하는 후속 비교·순위·지시어·가정형 fragment (`비싼거`, `2번째로 비싼거`, `이거 말고 더 있을건데`, `만약 5년 근무하면?` 류)
- `agent`: 서로 다른 규정 간 비교/추천, 별도 도구·외부 조회가 필요한 탐색

현재 `assets/prompts/chat/llm_router.md` 의 `agent: 비교·추천·예외·가설 시뮬레이션` 문구는 위 fragment 까지 agent 로 잡아먹을 위험이 있으므로, prompt 보강 + content guard 테스트로 고정한다.

| Case | Tier | Expected route | Rewrite 동작 | `_llm_classify` 호출 |
|---|---|---|---|---|
| `비싼거` | LLM (follow-up) | `single_shot` | 직전 turn 컨텍스트 병합 → 명시적 쿼리로 재작성 | ✅ 1회 |
| `2번째로 비싼거` | LLM (follow-up) | `single_shot` | 순위 지시어 보존하며 직전 주제 결합 | ✅ 1회 |
| `이거 말고 더 있을건데` | LLM (follow-up) | `single_shot` | 부정 + 동일 카테고리 추가 탐색 의도 보존 | ✅ 1회 |
| `만약 5년 근무하면?` | LLM (follow-up) | `single_shot` | 가정형 그대로 + 직전 주제(퇴직금 등) 결합 | ✅ 1회 |
| `급여 지급일은?` | DATE_CONDITION | agent (date) | rewriter 미경유 | ❌ 0회 |
| `지급 일` | DATE_CONDITION | agent (date) | rewriter 미경유 | ❌ 0회 |
| `정산일` | DATE_CONDITION | agent (date) | rewriter 미경유 | ❌ 0회 |
| `만료일` | DATE_CONDITION | agent (date) | rewriter 미경유 | ❌ 0회 |
| `마감일` | DATE_CONDITION | agent (date) | rewriter 미경유 | ❌ 0회 |

## 4. Out of Scope
- Router + Rewriter 를 단일 LLM 호출로 합치는 구조 변경
- 대규모 토큰/비용 최적화
- 검색엔진/청킹 파이프라인 개편

## 5. Patch Target (실제 수정/검증 대상)
- `chat.services.question_router._llm_classify`
  - history 전달 경로 확인 (직전 turn 이 prompt 에 실리는지)
  - LLM 응답 JSON parse / fallback 동작
  - token usage purpose 태깅
  - 테스트에서의 call-site mock (호출 횟수 검증 포함)
- `chat.services.query_rewriter._call_rewriter_llm`
  - follow-up 재작성 prompt (`assets/prompts/chat/query_rewriter.md`) 의 fragment/지시어 처리
  - 출력은 JSON 이 아니라 **한 줄 text**. `_clean_llm_output` 으로 정제 → `NOOP` sentinel / 길이 가드 / 예외 fallback (원문 유지) 동작 검증
- `assets/prompts/chat/llm_router.md`
  - follow-up fragment(비교/순위/지시어/가정형) 는 `single_shot` 으로 보내도록 가이드 문구 보강
  - 서로 다른 규정 비교/추천/도구 탐색만 agent 로 가도록 분리 예시 추가
- `chat.services.prompt_builder.build_messages`
  - 재작성 쿼리 + 원문 + history 주입 순서
- `chat.services.single_shot.pipeline`
  - router → rewriter → retrieval → prompt_builder 통합 흐름

**테스트 설계 분리 (중요)**: `run_single_shot` direct 호출은 router 가 이미 single_shot 으로 결정된 이후 단계만 검증할 수 있어, route 분기나 `_llm_classify` 호출 횟수는 단언할 수 없다. 따라서:

| 검증 대상 | 담당 테스트 파일 | 방식 |
|---|---|---|
| LLM Router prompt content guard, `_llm_classify` mock/parse, 호출 횟수 | `chat/tests/test_llm_router.py` (신규 또는 확장) | `_llm_classify` 를 직접 호출하거나 mock 으로 count |
| route 분기 (LLM tier vs DATE_CONDITION 우선순위, agent vs single_shot) | `chat/tests/test_routing_e2e.py` | router 진입점 e2e |
| Rewrite 동작 (follow-up fragment → 재작성 text, NOOP/fallback) | `chat/tests/test_query_rewriter.py` | rewriter direct |
| prompt 주입 순서, token usage purpose | `chat/tests/test_prompt_builder.py`, `chat/tests/test_token_usage_purpose_call_sites.py` | direct |
| follow-up rewrite + prompt 통합 흐름 | `chat/tests/test_router_followup_e2e.py` (신규) | `run_single_shot` direct 권장 — 이 파일은 9개 전체가 아니라 LLM tier 4건의 rewrite/prompt 부분만 담당 |

> 신규 e2e 가 `run_chat_graph` 를 쓸 경우: patch target 은 모듈 함수가 아니라 `chat.graph.app.<node>` binding 이며, setUp/tearDown 에서 `chat.graph.app._compiled_graph.cache_clear()` 호출 필수. 가능하면 그래프 우회 + `run_single_shot` direct 로 좁힌다.

## 8. 사용자 수동 QA 시나리오
URL: `http://localhost:8001/`

사전:
- BO `http://localhost:8001/bo/` dashboard 의 `LLM 라우터` 호출 카운트 baseline 기록 (`N0`).
- BO RouterRule 목록에 §3 fragile case 와 겹치는 rule 이 **없음** 을 확인. (DB RouterRule 이 가로채면 `route_reason=db_rule` 로 빠져서 LLM Router 카운트가 기대보다 덜 오름.)

### 시나리오 A — 경조사 비교/지시어 (LLM tier, follow-up)
입력 순서:
1. `경조사` → 경조사 항목 안내
2. `비싼거` → 최고 한도 항목: 기대 `본인 상 500만원` (자료 표기에 따름)
3. `2번째로 비싼거` → 두 번째 항목: 기대 `배우자 상 100만원` 류
4. `이거 말고 더 있을건데` → 동일 카테고리의 추가 항목 안내

### 시나리오 B — 가정형 follow-up (LLM tier)
1. `퇴직금 계산 기준 알려줘`
2. `만약 5년 근무하면?` → 5년 근속 가정 답변

### 시나리오 C — 동의어/축약형 날짜 (DATE_CONDITION tier)
1. `급여 지급일은?`
2. `지급 일`
3. `정산일`
4. `만료일`
5. `마감일`
→ 각각 의도에 맞는 규정 항목(급여/정산/만료/마감) 으로 date agent 라우팅.

### BO 카운트 기대
- 시나리오 A: `LLM 라우터` 카운트 `N0 → N0 + 4`
- 시나리오 B: `LLM 라우터` 카운트 `+2`
- 시나리오 C: DATE_CONDITION 은 LLM Router 를 건너뛰므로 **카운트 증가 없음**
- 합산 기대: `N0 + 6` (시나리오 C 입력 5건 제외)
- 주의 1: 현재 BO dashboard 에는 실패/타임아웃 카운트가 없으므로 그 항목은 확인하지 않는다.
- 주의 2: 위 기대값은 **DB RouterRule override 가 없는 clean 환경 기준**. BO 에 매칭 rule 이 있으면 `route_reason=db_rule` 로 빠져 LLM Router 카운트가 더 낮게 잡힐 수 있다. 사전 단계에서 rule 충돌 확인 필수.
