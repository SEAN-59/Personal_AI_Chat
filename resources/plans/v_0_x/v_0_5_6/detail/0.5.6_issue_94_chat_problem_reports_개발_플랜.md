# v0.5.6 — Issue #94 채팅 문제 제보(Chat Problem Reports) 개발 플랜

## 1. 목적과 범위

사용자가 채팅 화면에서 답변/사용자 경험에 문제가 있을 때, 현재 진행 중인 세션의 대화 전체(질문·답변·근거 sources)를 스냅샷으로 함께 첨부하여 관리자에게 제보할 수 있는 경로를 만든다. BO(백오피스)에는 별도 메뉴가 생기며, 관리자는 상태(status)와 관리자 메모(admin_note)를 갱신할 수 있다.

### In-scope
- 채팅 화면 헤더의 `초기화` 좌측에 `문제 제보` 버튼 추가.
- 버튼 클릭 시 모달: 제목/내용 입력 + "현재 대화 및 답변 근거가 관리자에게 전송됩니다" 고지.
- 제출 시 현재 세션 대화 전체(요약 아닌 raw) + 답변별 sources를 스냅샷으로 DB 저장.
- BO에 `문제 제보` 전용 리스트/상세 페이지, 상태 및 admin_note 갱신.

### Out-of-scope (이번 이슈에서 처리하지 않음)
- CanonicalQA / 운영 QA로의 자동 승격.
- 이메일 / 슬랙 / 푸시 등 외부 알림.
- 사용자 본인 제보 이력 조회 화면.
- 첨부 파일 업로드.
- thumbs-up/down 피드백, ChatLog 흐름과의 통합/통계.

## 2. 데이터 모델 & 마이그레이션

### 2.1 신규 모델 `ProblemReport` (in `chat/models.py`)

| 필드 | 타입 | 비고 |
|------|------|------|
| `id` | AutoField (PK) | |
| `title` | CharField(max_length=120) | 사용자 입력. 트림 후 최소 1자, 최대 120자 |
| `content` | TextField | 사용자 입력. 최대 길이는 DB는 무제한이나 폼/엔드포인트에서 4,000자 캡 |

| `conversation` | JSONField(default=list) | 아래 §2.2 스키마를 따르는 turn 배열 스냅샷 |

| `created_at` | DateTimeField(auto_now_add=True, db_index=True) | |
| `updated_at` | DateTimeField(auto_now=True) | |

`STATUS_CHOICES = (('open','신규'),('in_progress','확인 중'),('resolved','해결'),('wontfix','보류'))`

Meta: `ordering = ['-created_at']`, `verbose_name = '문제 제보'`.

### 2.2 `conversation` JSON 스키마 (스냅샷)

스냅샷은 **서버가 `/message/` 처리 시점에 turn 단위로 누적**한 결과를 그대로 저장한다(§4.3). ChatLog 텍스트 매칭은 사용하지 않는다.

```json
[
  {
    "role": "user",
    "content": "string",
    "ts": "2026-05-18T12:34:56Z"   // 해당 turn append 시각(ISO8601 UTC)
  },
  {
    "role": "assistant",
    "content": "string",            // run_chat_graph가 반환하고 UI에 내려준 reply 그대로
    "sources": [                    // run_chat_graph가 반환하고 UI에 내려준 sources 그대로
      {"name": "...", "url": "..."} // 현재 런타임 스키마: name/url 딕셔너리. title/score/snippet 등 임의 필드를 만들어내지 않는다.
    ],
    "chat_log_id": 123,             // run_chat_graph 결과의 chat_log_id (있을 때만)
    "ts": "2026-05-18T12:34:57Z"
  }
]
```

- 시스템 프롬프트는 스냅샷에 **절대 포함하지 않는다** (PII/내부 지침 노출 방지).
- `sources`는 어시스턴트 turn에만 존재하며, 응답에 내려간 dict 리스트를 문자열 트림 후 그대로 저장한다.
- `chat_log_id`는 어시스턴트 turn에만 존재한다.
- 누락된 `sources`는 빈 리스트로, 누락된 `chat_log_id`는 키 자체를 생략하거나 `null`로 둔다(테스트에서 한쪽 형식으로 고정).

### 2.3 마이그레이션
- 파일: `chat/migrations/0017_problemreport.py` (자동 생성; `makemigrations chat`).
- 인덱스: `status`, `created_at`, `session_key`(개별).
- pgvector 확장 의존 없음 — 임베딩 없음.

### 2.4 사이즈/프라이버시 가드
- 본 기능이 캡처하는 범위는 **"현재 세션의 보고용 스냅샷(append-only, 캡 적용)" 한정**이며, 무한 누적이 아니다.
- 서버 측 보고 스냅샷 키: `SESSION_REPORT_SNAPSHOT_KEY = 'problem_report_snapshot'` (세션에 별도 저장; `chat_history`와 **분리**됨).
- 누적/저장 규칙:
  - **메시지 100개**(user/assistant turn 각각을 1개로 셈)를 상한으로 한다. 초과 시 가장 오래된 메시지부터 폐기(앞쪽 트림). 본 문서 전체에서 "메시지"라는 단어로 단위를 통일한다.
  - `turn_count` = 캡 적용 후 conversation에 저장된 메시지 수(user/assistant 각각 1개, system 제외).
- 정규화:
  - 각 메시지 `content` 8,000자 캡(초과 시 말미 `…`).
  - `sources[i]` 내 모든 문자열 값은 500자 캡(현재 스키마: `name`, `url`).
  - 시스템 프롬프트/시스템 role 메시지, 빈 메시지는 스킵.
- 사용자 IP/UA는 저장하지 않는다(개인정보 최소화).

## 3. API 엔드포인트 계약

### 3.1 `POST /report/`  (chat 앱)
- URL conf: `chat/urls.py` — `path('report/', views.problem_report, name='problem_report')`
- 데코레이터: `@require_http_methods(['POST'])` + 기본 Django CSRF.
- 요청 헤더: `Content-Type: application/json`, `X-CSRFToken: <token>`.
- 요청 바디:
  ```json
  {"title": "...", "content": "..."}
  ```
- 검증:
  - `title` trim 후 1~120자, 비어 있으면 400 `{"error":"title_required"}`.
  - `content` trim 후 1~4000자, 비어 있으면 400 `{"error":"content_required"}`.
  - JSON 파싱 실패 시 400 `{"error":"invalid_json"}`.
- 처리:
  1. `get_report_snapshot(request)`로 서버에 누적된 보고용 스냅샷을 읽는다(없으면 `[]`).
  2. `sanitize_report_snapshot(snapshot)`으로 §2.4 규칙(메시지 100개 캡, content 8,000자, sources 문자열 500자, system/빈 메시지 제외)을 적용한다.
  3. `last_question` = 정규화된 스냅샷에서 가장 마지막 `role=='user'` 메시지의 `content[:500]` (없으면 `''`).
  4. `turn_count` = 정규화된 스냅샷에 저장된 메시지 수(user/assistant 각각 1개, system 제외).
  5. `session_key` = `request.session.session_key or ''` (없으면 `request.session.save()` 후 재독).
  6. `ProblemReport.objects.create(conversation=정규화된 스냅샷, ...)`.
- 응답 200:
  ```json
  {"ok": true, "id": 42}
  ```
- 응답 에러: 400(검증), 405(method).
- **프론트엔드는 대화 데이터를 전송하지 않는다.** 페이로드는 `{title, content}`만 받는다. 서버가 이미 가지고 있는 `problem_report_snapshot`을 사용한다.
- 본 엔드포인트는 `chat_history`와 `problem_report_snapshot` 어느 쪽도 **변경하지 않는다** (대화 진행 중 제보는 비파괴).

### 3.2 BO 엔드포인트
- `GET  /bo/reports/` — 목록 (필터: status, q=title/content/last_question 부분일치, 페이지네이션).
- `GET  /bo/reports/<int:pk>/` — 상세.
- `POST /bo/reports/<int:pk>/update/` — `status` 또는 `admin_note` 갱신. `next` 파라미터로 redirect.
  - 필드 검증: status는 choices 내, admin_note 길이 4000자 캡.

### 4.3 보고용 스냅샷의 서버 측 누적 — `chat/services/history_service.py` (또는 신규 `chat/services/report_snapshot.py`)

채택 방향은 **서버가 `/message/` 처리 시점에 보고용 스냅샷을 누적**하는 것이다. ChatLog 텍스트 매칭 휴리스틱(이전 안)은 **폐기한다**.

세션 키:

```
SESSION_REPORT_SNAPSHOT_KEY = 'problem_report_snapshot'
```

헬퍼 계약(시그니처/책임):

- `append_report_snapshot_turn(request, user_text, result) -> None`
  - `/message/`의 `run_chat_graph(...)` 호출 직후 1회 호출한다.
  - `result`는 `chat.services.single_shot.types.QueryResult` dataclass 인스턴스다(dict 아님). 속성 접근(`result.reply`, `result.sources`, `result.chat_log_id`)을 사용한다.
  - 다음 두 메시지를 순서대로 append 한다(공통 ts = 현재 UTC, ISO8601):
    1. `{"role": "user", "content": user_text, "ts": ts}`
    2. `{"role": "assistant", "content": result.reply, "sources": result.sources or [], "chat_log_id": result.chat_log_id, "ts": ts}`
       - `result.reply` / `result.sources` / `result.chat_log_id`는 UI에 내려가는 것과 **동일한 값**을 그대로 저장한다.
  - append 후 §2.4 규칙에 따라 길이 캡 적용 + 메시지 100개 초과 시 앞쪽 트림.
  - 세션 미수정 트리거를 위해 `request.session.modified = True` 보장.
- `get_report_snapshot(request) -> list[dict]`
  - 세션에서 스냅샷을 읽어 반환(없으면 `[]`). 사이드이펙트 없음.
- `clear_report_snapshot(request) -> None`
  - 세션에서 `SESSION_REPORT_SNAPSHOT_KEY`를 제거.
- `sanitize_report_snapshot(snapshot) -> list[dict]`
  - **이미 캡처된 보고 메시지 리스트**에 대해서만 정규화한다(시스템/빈 메시지 제거, content/문자열 길이 캡, 100개 컷, 알 수 없는 키 드롭). ChatLog 조회/텍스트 매칭을 하지 않는다.

`/message/` 통합 지점(요지, 코드 변경 위치만 기술):
- 기존 `chat_history` 갱신 로직은 **그대로 둔다**(LLM 컨텍스트용).
- `run_chat_graph` 반환 직후, 정상 응답 경로에서 `append_report_snapshot_turn(...)`을 호출한다.
- `chat_history`는 보고와 무관하게 자체 캡(현행)을 유지한다. `problem_report_snapshot`은 자체 100메시지 캡을 가진다(병렬, 상호 독립).

`/reset/` 통합 지점:
- 기존 `chat_history` 클리어와 동시에 `clear_report_snapshot(request)`를 호출한다. 사용자는 리셋 후 완전히 새로운 세션을 기대한다.

  - `status` select.
  - `admin_note` textarea (4000자 캡).
  - 저장 후 동일 상세로 redirect(`next` 미사용 기본).

## 8. 테스트 플랜 (오프라인, 외부 호출 없음)

### 8.1 모델 — `test_problem_report_model.py`

- choices 검증: 잘못된 status로 `full_clean()` 시 `ValidationError`.

### 8.2 스냅샷 헬퍼 — `test_problem_report_snapshot.py`
- `append_report_snapshot_turn`: `run_chat_graph` 반환값을 mocked `QueryResult` dataclass 인스턴스(`reply` / `sources` / `chat_log_id` 속성)로 만들어 전달하고, 그 속성값이 그대로 스냅샷에 저장됨을 확인한다. user 메시지와 assistant 메시지 두 개가 순서대로 append 됨. (dict 반환을 가정하지 않는다.)
- 시스템 role / 빈 content 메시지는 `sanitize_report_snapshot`에서 제외됨.
- 8,000자 초과 content 말미 잘림 + `…` 처리.
- `sources` 항목의 문자열 값(`name`, `url`)이 500자로 트림됨.
- 100메시지 초과 시 앞쪽 트림 후 최근 100개만 유지.
- 빈 스냅샷 → `sanitize_report_snapshot([]) == []`.
- `clear_report_snapshot` 호출 후 세션 키가 사라짐. **ChatLog 텍스트 매칭 휴리스틱 테스트는 포함하지 않는다(해당 로직 자체가 없음).**

### 8.3 `/message/` · `/reset/` 통합 — 같은 파일 또는 `test_problem_report_endpoint.py`

- `/reset/` 호출 시 `chat_history`와 `problem_report_snapshot`이 **둘 다** 제거됨을 확인.

### 8.4 `/report/` 엔드포인트 — `test_problem_report_endpoint.py`
- 정상 POST → 200, DB 1건. 저장된 `conversation`은 사전 누적된 보고 스냅샷의 정규화 결과와 동일.

- content 4001자 → 400.
- 잘못된 JSON → 400.

- 스냅샷이 비어 있는 세션에서도 200, 저장된 `conversation=[]`, `last_question=''`, `turn_count=0`.
- 제보 후에도 `chat_history`와 `problem_report_snapshot`이 **변경되지 않음**을 확인(비파괴).

## 10. 위험 요소 및 명시적 한계

- 보고용 스냅샷은 **현재 세션 한정, 메시지 100개 캡까지만** 캡처한다. 무한 누적이 아니며, 초과분은 앞쪽부터 폐기된다.
- 스냅샷 `ts`는 해당 turn이 서버에 append 된 시각이다(스냅샷 생성 시각 일괄 부여가 아님). 다만 동일 `/message/` 호출의 user/assistant 두 메시지는 동일 ts를 공유한다.
- `chat_history`(LLM 컨텍스트)와 `problem_report_snapshot`(보고용)은 **병렬·독립**이며 각자 캡을 가진다. 보고 동작은 둘 다 변경하지 않으며, `/reset/`은 둘 다 클리어한다.
- `sources` 스키마는 현재 런타임이 내려주는 형태(`name`/`url`)를 그대로 저장한다. 임의 필드(title/score/snippet 등)는 만들어내지 않는다.
- 사용자가 모달에 입력한 text 외 PII는 수집하지 않는다(IP/UA 저장 금지).
- 시스템 프롬프트 본문은 스냅샷에 절대 포함하지 않는다.
