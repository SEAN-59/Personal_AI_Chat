# v0.5.2 Input Normalization Rules 개발 플랜

- Issue: #85 feat: Add BO-managed input normalization rules
- Milestone: v0.5.2: Input Normalization
- Branch: `feature/85-input-normalization-rules`
- Base: `develop`

---

## 0. TL;DR
사용자가 채팅창에 입력한 raw 질문에 대해, BO에 등록된 규칙만으로 **사내 용어/오타 보정**을 수행하는 데이터 주도(Data-driven) 정규화 레이어를 도입한다. 코드에는 어떤 사내 용어 사전도 하드코딩하지 않는다. raw 입력은 절대 덮어쓰지 않고, normalized 결과는 라우팅/검색 등 내부 처리용으로만 사용한다.

---

## 1. 배경 / 목표
- 사용자가 사내 약칭, 채팅체 단축어, 흔한 오타(`rudwhtk → 경조사`, 한영 오타 등)를 입력해도 같은 답이 돌아오게 만들고 싶다.
- 그러나 사내 용어 사전을 코드에 박는 순간 운영팀이 손댈 수 없고, 업종/도메인이 바뀔 때마다 코드 PR이 필요해진다.
- 따라서 운영자가 BO에서 직접 규칙을 등록/수정/비활성화할 수 있는 **InputNormalizationRule** 을 만들고, 라우터 진입 직전에 정규화 레이어를 한 번만 적용한다.

### 비목표 (Non-goals)
- 한국어 자동 맞춤법/오타 교정기 (HanSpell, KoBART 등) 도입 — out of scope.
- 형태소 분석 기반 동의어 확장 — out of scope.
- 기본 seed 데이터 — 원칙적으로 **out of scope**. 마이그레이션은 빈 테이블만 생성한다 (이유: §1 의 데이터 주도 원칙). 데모용 fixture 도 별도 파일로만 제공하고 자동 load 하지 않는다.

## 3. 핵심 결정 사항 / Plan-level 리스크

### 3.1 핵심 결정 (반드시 박제)
| ID | 결정 | 이유 |
|---|---|---|
| D1 | 코드/마이그레이션/seed 어디에도 **사내 용어 사전을 하드코딩하지 않는다**. | 운영팀이 BO 만으로 운용 가능해야 한다. 코드에 박히면 도메인 전환 비용이 폭증. |
| D2 | raw 입력은 절대 덮어쓰지 않는다. UI/ChatLog 표시값은 항상 `question_raw`. | 회귀/디버깅/사후 분석에서 사용자가 실제 무엇을 쳤는지가 진실 소스. |
| D3 | normalized 는 **router 진입 직전 1회** 적용. graph 노드 내부에서 추가 normalize 금지. | 다중 적용 시 의도치 않은 체이닝 발생 위험. 단일 진입점이 추적성도 좋다. |
| D4 | router(`question_router`), `query_rewriter`, retrieval(`qa_retriever`), agent, workflow 모두 normalized 를 받는다. ChatLog/UI 표시는 raw. | 분기/검색 품질은 정규화된 텍스트로 평가. 사용자 표시는 원문. |
| D5 | exact match 가 contains 보다 우선. 동률이면 `priority` DESC, 그 다음 `id` ASC. | contains 의 과잉적용 리스크를 구조적으로 차단. |
| D6 | **Single best rule 정책 (v0.5.2 한정)**: 한 번의 정규화 호출에서 최대 **1개 규칙만** 적용한다. 모든 매칭은 `q_canon = canonicalize(question)` 기준. exact 매치가 1건이라도 있으면 (priority DESC, id ASC) 1건 적용 후 즉시 종료. exact 가 없을 때만 contains 후보 중 (priority DESC, id ASC) 1건을 `q_canon.replace(rule.pattern, rule.replacement, 1)` 로 적용 후 종료. raw `question` 에 직접 replace 하지 않음 (전각/반각/대소문자 차이로 매치 자리가 빗나가는 사고 방지 — §6.2 와 동일 계약). 다중 체이닝/fixed-point/MAX_APPLIES 는 후속 scope. | exact 적용 결과에 contains 가 다시 걸려 `급여 정산일` → `급여 정산일일` 같은 오버랩 사고가 발생할 수 있음(Codex v1 finding 1). v0.5.2 는 안전쪽으로 단순화. |
| D7 | replacement 가 비었거나 trim 후 길이 < 1 인 규칙은 적용하지 않는다(저장은 막는다). 입력이 비거나 공백만이면 normalize 자체를 skip. | 빈 치환으로 질문 자체가 사라지는 사고 방지. |
| D8 | DATE_CONDITION / DB RouterRule / LLM Router / query_rewriter 우선순위는 **변경하지 않는다**. 정규화는 그들 앞단에서만 동작한다. | 기존 안정화된 라우팅 계약([[project_v0_5_0_llm_router]], v0.5.1) 을 깨지 않는다. |

### 3.2 Plan-level 리스크
- **R1 (contains 과잉 적용)**: `사`라는 짧은 contains 규칙이 들어오면 거의 모든 문장에 적용. → BO form 에 `match_type=contains` 일 때 `pattern` 최소 길이(예: 2자) validation. 운영 문서에도 명시.
- **R2 (RouterRule 과의 충돌)**: BO RouterRule 이 `경조사` 같은 키워드를 가로채고 있는 상태에서 InputNormalizationRule 이 `rudwhtk → 경조사` 를 만들면, normalized 가 RouterRule 에 잡혀 route 가 바뀐다. → **의도된 동작**으로 명문화. dev log 에 박제. 수동 QA 시나리오에 포함.
- **R3 (query_rewriter 와 이중 적용)**: rewriter 가 follow-up fragment 를 재작성할 때 normalized 입력을 받으면 의미가 더 명확해져 도움이 됨. 반대로 raw 를 받게 두면 오타로 인해 rewrite 가 실패. → rewriter 는 normalized 만 본다. raw 는 history 출력/ChatLog 에만.
- **R4 (LLM Router prompt 와의 충돌)**: prompt 에 raw 가 섞이면 분류기가 흔들림. → 분류기 입력에도 normalized 만 전달.
- **R5 (정규화 trace 가 사라짐)**: 운영이 “왜 이렇게 답이 갔지” 진단하려면 어떤 rule 이 적용됐는지 보여야 함. → `normalization_applied` (matched rule id/pattern/replacement 리스트, 길이 0 또는 1) 를 **GraphState 와 서버 로그에만** 남긴다. ChatLog 에는 `normalized_question` 텍스트만. ChatLog 에 JSON trace 컬럼은 추가하지 않음 (§4.2).
- **R6 (관리자 권한 누수)**: BO 화면이 무인증으로 노출되면 외부에서 모든 입력을 가로채는 치환 규칙을 심을 수 있음(보안 영향). → **본 스코프에서는 기존 BO 패턴과 동일하게 decorator 없이 진행** (§5.3 확정). CSRF 토큰 + POST 보호만 다른 BO CRUD 와 동일하게 유지. BO 전체 인증(staff_required/login_required) 도입은 v0.6.x 후속 별도 이슈로 분리. dev log / PR 본문에 본 위험을 명시해 운영팀이 인지하도록 한다.
- **R7 (Unicode/대소문자/공백 정규화)**: `rudwhtk` vs `Rudwhtk`, 끝 공백, 전각/반각 차이로 exact match 가 빗나감. → **중립 모듈에 helper 정의** (Codex v3 finding 1 — 순환 import 방지):
  ```python
  # chat/utils/text_normalization.py  (신규, 다른 모듈에 의존하지 않음)
  import unicodedata
  def canonicalize(text: str) -> str:
      return unicodedata.normalize('NFKC', text or '').strip().casefold()
  ```
  - `chat/models.py` 와 `chat/services/input_normalizer.py` 가 **둘 다 이 helper 만** import 한다. `input_normalizer.py` 는 `chat.models.InputNormalizationRule` 도 import 해야 하므로, helper 를 `input_normalizer.py` 안에 두면 `models → input_normalizer → models` 순환 import 가 발생한다. 중립 모듈로 분리해 차단.
  - **저장 단 (보장 범위 명시 — finding 2)**: `InputNormalizationRule.clean()` + `save()` 에서 `self.pattern = canonicalize(self.pattern)` 적용. **보장 경로**: ModelForm save, Django admin save, `Model(...).save()` instance 저장, `objects.create(...)`. **비보장 경로 (v0.5.2 운영 금지 또는 후속 scope)**: `QuerySet.update(pattern=...)`, `bulk_create()`, `loaddata`/fixture, raw SQL. 이들 경로는 `save()` 를 우회하므로 canonical 보장이 깨질 수 있음 — 운영 가이드/dev log 에 명시. custom manager/queryset 도입은 본 스코프 비포함.
  - **비교 단**: 서비스에서 exact 매치 비교는 `canonicalize(question)` 과 (이미 canonical 인) `rule.pattern` 직접 비교. contains 매치도 `canonicalize(question)` 안에서 `rule.pattern` 의 부분 문자열 매치를 본다 (raw `question` 직접 매치 금지 — 그렇지 않으면 전각/반각/대소문자 차이로 빗나간다).
  - **출력 단**: 결과 텍스트는 `replacement` 를 그대로 사용 (BO 운영자가 입력한 원형 유지). raw 의 양옆 공백/대소문자는 결과에 영향을 주지 않는다.
  - **replacement 는 canonicalize 하지 않는다**. 표시용 한글이 NFKC 로 바뀌면 운영자의 의도와 다를 수 있음.

## 4. 모델 / 마이그레이션

### 4.1 `chat.InputNormalizationRule`
```
class InputNormalizationRule(models.Model):
    pattern       = CharField(max_length=200)            # 입력 키 (예: "rudwhtk")
    replacement   = CharField(max_length=200)            # 정규화 결과 (예: "경조사")
    match_type    = CharField(choices=[('exact','exact'),('contains','contains')], default='exact')
    enabled       = BooleanField(default=True)
    priority      = PositiveIntegerField(default=100)    # 클수록 먼저
    description   = CharField(max_length=300, blank=True)
    created_at    = DateTimeField(auto_now_add=True)
    updated_at    = DateTimeField(auto_now=True)
```

#### Unique / 중복 정책
- DB unique: `("pattern", "match_type")` UniqueConstraint. `pattern` 저장 시 §3.2 R7 의 `canonicalize()` (NFKC + strip + casefold) 가 모델 `clean()`/`save()` 에서 강제 적용된 값을 기준으로 함.
- **보장 경로**: ModelForm, Django admin, `Model(...).save()`, `objects.create(...)` — 모두 canonical 형태로 DB 에 들어간다.
- **비보장 경로** (Codex v3 finding 2): `QuerySet.update(pattern=...)`, `bulk_create()`, `loaddata`/fixture, raw SQL 은 `save()` 를 우회하므로 canonical 보장 없음. v0.5.2 에서는 운영상 사용 금지로 명시(dev log/PR 본문). 진짜 보장하려면 custom manager/queryset 이 필요하나 본 스코프 비포함 — 후속 이슈.
- 같은 pattern 이라도 `match_type` 이 다르면 별개로 허용 (예: exact:`지급일` 과 contains:`지급일` 공존 가능).
- **validation 책임 일원화 (Codex v3 finding 3)**: 핵심 검증 3건은 **`InputNormalizationRule.clean()`** 에 둔다. ModelForm 은 `Meta.model = InputNormalizationRule` + `full_clean()` 호출로 model validation 을 그대로 사용하고, UX 에 맞는 한국어 에러 메시지만 form `clean()` 에서 ValidationError 메시지 텍스트를 다듬는다. → BO 우회 경로(`objects.create(...)`, admin) 에서도 동일 검증이 작동.
  - V1: contains 규칙은 `len(canonicalize(pattern)) < 2` 이면 reject.
  - V2: `canonicalize(pattern) == canonicalize(replacement)` 이면 reject (no-op 규칙 방지).
  - V3: `replacement.strip()` 빈 값 reject.
- **canonicalize 적용 순서 (Codex v4 finding 1)**:
  - `InputNormalizationRule.clean()` 의 **첫 줄**에서 `self.pattern = canonicalize(self.pattern)` 를 적용한다 (mutating canonicalization). 이렇게 해야 이어지는 V1~V3 검증과 Django 의 `validate_unique()` 가 **canonical 값 기준**으로 돌아 false positive/negative 가 발생하지 않는다.
  - 모델 `save()` 순서는 `canonicalize(필요 시 보강) → full_clean() → super().save()`. 구체적으로:
    ```python
    def clean(self):
        self.pattern = canonicalize(self.pattern)
        # V1~V3 검증
        ...

    def save(self, *args, **kwargs):
        # full_clean 이 clean() 을 호출하면서 canonicalize + V1~V3 + validate_unique 를 모두 수행
        self.full_clean()
        return super().save(*args, **kwargs)
    ```
  - ModelForm `is_valid()` 도 내부적으로 `instance.full_clean()` → `instance.clean()` 경로를 거치므로, 첫 줄 canonicalize 가 form 단계의 `validate_unique()` 에도 canonical 값을 보게 한다.
  - **잘못된 순서 (회피)**: `full_clean → canonicalize → super().save()` 는 unique 검증이 비-canonical 값으로 먼저 돌아, DB 에 `rudwhtk` 가 있는 상태에서 사용자가 `RUDWHTK  ` 를 저장하려 할 때 `full_clean()` 의 unique 검증은 통과하고 super().save() 단계에서 IntegrityError 로 터지는 사고 가능.

#### 마이그레이션
- 모델 생성 + 빈 테이블만. **데이터 마이그레이션 없음.**
- 인덱스: `(enabled, priority)` composite index 정도만 추가 검토. 대량 운영을 가정하지 않으므로 기본만 유지.

### 4.2 ChatLog (운영 가시성, 최소) — Codex finding 6
- 새 필드 1개: `normalized_question = TextField(blank=True, default='')`.
  - 기존 `ChatLog.question` 이 TextField 이므로 타입 일치. CharField(4000) 으로 잡으면 긴 질문/치환 확장 시 불필요한 길이 리스크.
  - 비어 있으면 “정규화가 일어나지 않았음 (raw 와 동일)” 을 뜻한다.
- **trace 용어 통일**: 적용된 규칙 메타 리스트는 `normalization_applied` 로 부른다. **state / 서버 로그 전용**이며 ChatLog 컬럼으로는 저장하지 않는다. (이전 초안의 `normalization_meta` 표현은 본 문서 전반에서 `normalization_applied` 로 통일.)
- 별도 `applied_rules` JSON 필드는 **이번 스코프에서 추가하지 않는다** — ChatLog 스키마 변경을 최소화. 디버깅용 trace 는 server log + state 디버그 키로만 노출.
- 적용 횟수/`last_applied_at` 같은 운영 지표는 **out of scope**. 추후 v0.5.x 후속 또는 0.x maintenance ([[project_0_x_maintenance]]) 에서 별도 이슈.

### 5.3 권한 (Codex finding 5)
- **현재 BO views 는 `staff_required`/`login_required` decorator 가 적용되어 있지 않다** (`bo/views/router_rules.py` 외 다른 view 들도 동일). 본 스코프에서 새 인증을 도입하면 BO 전체 정책 영향이 되어 별도 risk/scope 가 필요하다.
- **본 PR 의 결정**: 기존 BO 패턴과 **동일하게 decorator 없이** 진행. CSRF 토큰 + POST 보호만 다른 BO CRUD 와 동일하게 유지. BO 전체 인증 도입은 v0.6.x 후속 별도 이슈로 분리.
- dev log / PR 본문에 “BO 인증은 v0.5.2 스코프 밖” 을 명시.

## 6. 정규화 서비스 (`chat/services/input_normalizer.py`)

### 6.1 공개 API
```
def normalize(question: str) -> NormalizationResult:
    """raw 질문에 BO 규칙을 적용해 정규화 결과를 반환.

    Returns:
        NormalizationResult(
            raw: str,
            normalized: str,
            applied: list[AppliedRule],   # 적용된 규칙 메타
            changed: bool,
        )
    """
```
- `AppliedRule = dataclass(id:int, pattern:str, replacement:str, match_type:str)`.
- `raw` 는 입력 그대로 (절대 변형 금지).
- `normalized` 가 raw 와 동일하면 `changed = False`, `applied = []`.

### 6.2 알고리즘 (single best rule, v0.5.2 한정 — D6)
1. `question` 이 None / 빈 문자열 / 공백만이면 즉시 `(raw, raw, [], False)` 반환 (D7).
2. 활성 규칙 로딩: `InputNormalizationRule.objects.filter(enabled=True).order_by('-priority', 'id')`. 결과를 (a) exact 그룹, (b) contains 그룹 으로 분리.
3. `q_canon = canonicalize(question)` (NFKC + strip + casefold).
4. **Step 1 — exact 우선**: `q_canon` 이 exact 규칙의 (저장 시 이미 canonical 인) pattern 과 일치하는 규칙을 priority DESC, id ASC 순으로 1건 선택. 매치되면 `normalized = rule.replacement` 로 전체 치환하고 **즉시 종료**. `applied = [rule]`.
5. **Step 2 — contains (exact 가 한 건도 없을 때만)**: contains 규칙을 priority DESC, id ASC 순으로 순회하며 `rule.pattern in q_canon` 인 **첫 1건**을 선택. 결과 텍스트는 `q_canon.replace(rule.pattern, rule.replacement, 1)` 후 **즉시 종료**. `applied = [rule]`. (raw `question` 에 직접 replace 하지 않는 이유: 전각/반각/대소문자 차이로 매치는 됐지만 치환 자리가 빗나가는 사고 방지.)
6. 어느 단계에서도 매치가 없으면 `(raw, raw, [], False)`.
7. replacement.strip() 가 빈 값이면 해당 규칙은 skip 후 다음 후보 검토 (D7 — 저장 단에서 막지만 2중 가드).
8. `applied` 는 항상 길이 0 또는 1. 다중 적용은 v0.5.2 에서 의도적으로 차단. fixed-point/MAX_APPLIES 같은 안전가드는 본 스코프 비포함.

### 6.3 캐싱 정책
- v0.5.2 에서는 캐시 도입 없이 매 요청 쿼리. (운영 데이터 보고 v0.6.0 ([[project_v0_6_0_search_quality]]) 와 함께 재평가.)
- DB 라운드트립을 줄이고 싶으면 `lru_cache` 가 아닌 “요청 시작 시 1회 select + 메모리에서 매치” 패턴을 사용. 캐시는 명시적으로 후속 작업.

### 7.1 적용 지점

### 7.2 GraphState 확장 (`chat/graph/state.py`)
```
question: str                # = raw 유지 (기존 의미 보존, deprecation 예정 X)
question_raw: str            # 신규: 명시적으로 raw (UI/ChatLog 용)
question_normalized: str     # 신규: router/retrieval/agent/workflow 용
normalization_applied: list[dict]  # 신규: AppliedRule.__dict__ 직렬화 (서버 로그용 최소 trace)
```
- `question` 의 의미를 바꾸지 않기 위해 `question_raw` 를 따로 둔다. 기존 코드/테스트의 `state['question']` 참조를 한 번에 다 바꾸지 않는다.
- 호환을 위해 normalize 노드에서 `question_normalized` 가 비면 raw 로 fill.

### 7.2a 각 graph 노드의 state 접근 계약 (Codex finding 5)
`GraphState.question` 은 raw 의미를 유지(§7.2)하므로, 정규화 결과를 실제 라우팅/검색에 적용하려면 각 노드가 **명시적으로** `question_normalized` 를 읽어야 한다. 그러지 않으면 정규화 노드가 state 만 채우고 실제 동작은 raw 로 흐른다.

공용 헬퍼 패턴 (구현 시 동일하게 적용):
```python
def _processing_question(state) -> str:
    return state.get('question_normalized') or state['question']

def _raw_question(state) -> str:
    return state.get('question_raw') or state['question']
```

노드별 계약:
| 노드 | 처리용 입력 | raw 전달 | 비고 |
|---|---|---|---|
| `router_node` | `_processing_question(state)` | — | DB RouterRule / DATE_CONDITION / LLM Router 분류기 입력에 사용 |
| `single_shot_node` | `_processing_question(state)` | `_raw_question(state)` | `run_single_shot(normalized_question=..., raw_question=..., normalization_applied=state.get('normalization_applied') or [])` 호출 (§7.3a) |
| `workflow_node` | `_processing_question(state)` | `_raw_question(state)` | workflow_input_extractor 입력 + single_shot fallback 도 동일 |
| `agent_node` | `_processing_question(state)` | `_raw_question(state)` | 도구 인자 및 disabled/fallback 분기 모두 동일 |

### 7.3 각 모듈이 보는 값
| 모듈 | 입력 | 비고 |
|---|---|---|
| `question_router._evaluate` (DB RouterRule 매칭, DATE_CONDITION, LLM Router 분류 입력) | normalized | DATE_CONDITION 우선순위는 그대로 유지(D8). RouterRule 매치도 normalized 기준. |
| `query_rewriter._call_rewriter_llm` | normalized + history | rewriter prompt 에 raw 를 절대 노출하지 않음. |
| `qa_retriever` (검색 쿼리) | normalized (rewriter 결과가 있으면 rewriter 결과 우선) | 기존 우선순위 계약 변경 없음. |
| agent 노드들 | normalized | 도구 입력/툴 인자에도 normalized. |
| workflow 노드들 | normalized | workflow_input_extractor 도 normalized 기반. |
| prompt_builder (LLM 응답 생성) | normalized | LLM 입력 메시지에 사용자 질문은 normalized 로. |
| **UI / ChatLog / history 저장** | **raw** | (D2) |

### 7.3a 시그니처 변경 계약 (Codex finding 2)
현재 `chat.services.single_shot.pipeline.run_single_shot(question, history=None)` 은 단일 `question` 문자열을 rewriter / retrieval / prompt_builder / `persist_chat_log` 까지 그대로 흘려보낸다. 정규화를 끼우려면 raw 와 normalized 두 값을 함께 들고 다녀야 하므로 시그니처를 명시적으로 바꾼다.

**확정 시그니처** (구현 단계에서 그대로 채택):
```
def run_single_shot(
    normalized_question: str,
    history: Optional[List[Dict]] = None,
    *,
    raw_question: Optional[str] = None,           # None 이면 normalized_question 과 동일하다고 간주
    normalization_applied: Optional[list[dict]] = None,
) -> QueryResult: ...
```
- 첫 번째 positional 인자는 **normalized**. 내부에서 rewriter/retrieval/prompt_builder 입력으로 사용.
- ChatLog 저장은 `raw_question or normalized_question` 을 `question` 필드로, `normalized_question` 을 별도 컬럼으로 저장 (§4.2, finding 3 과 정합).
- 기존 호출자 보호: `raw_question` 생략 시 `raw = normalized` 로 채워, 정규화가 없는 코드 경로에서도 동작 변화 없음.

**연동 대상 호출처** (구현 시 동일 raw/normalized 전달):
- `chat.graph.nodes.single_shot.single_shot_node`
- `chat.graph.nodes.workflow.workflow_node` 의 single_shot fallback 분기
- `chat.graph.nodes.agent.agent_node` 의 disabled / fallback 분기
- view 직접 호출이 있다면 동일 적용 (확인 필요)

**`persist_chat_log` 계약 변경**:
```
def persist_chat_log(
    question: str,            # raw (UI/표시용 진실 소스)
    reply: str,
    chunk_hits: List[ChunkHit],
    *,
    normalized_question: str = '',   # raw 와 동일하거나 적용된 결과. 비어있으면 정규화 없음.
) -> Optional[int]: ...
```
- 내부에서 `save_chat_log(question=raw, normalized_question=normalized, ...)` 호출.

**`save_chat_log` 계약 변경** (`chat/services/qa_retriever.py`):
```
def save_chat_log(
    question: str,                  # raw, ChatLog.question 에 그대로 저장
    answer: str,
    sources: Optional[list] = None,
    *,
    normalized_question: str = '',  # 비어있으면 raw 와 동일하다고 간주
) -> ChatLog: ...
```
- ChatLog 저장 시 raw 와 normalized 를 모두 적재. embedding/dedup 정책은 §7.3b 참조.

### 7.3b ChatLog embedding / dedup / promotion 정책 (Codex finding 3)
- ChatLog.`question` = **raw** (사용자가 친 그대로). UI/표시/진실 소스.
- ChatLog.`normalized_question` = 정규화 결과 (변경 없으면 빈 문자열).
- **embedding/dedup 키**: `normalized_question or question` (즉 정규화 결과가 있으면 그것 우선, 없으면 raw). → typo ChatLog 가 별도 cluster 로 누적되는 오염을 막는다.
- `promote_to_canonical(chat_log)` → CanonicalQA 의 공식 질문은 `chat_log.normalized_question or chat_log.question`. raw typo 가 공식 Q&A 로 promote 되는 사고 방지.
- Tradeoff (문서화): UI 의 ChatLog 목록에 표시되는 `question` 은 raw 라서 운영자가 “이 ChatLog 가 어떤 문장으로 embedding 되었는지”를 한 눈에 알기 어렵다. **본 스코프에서는 BO ChatLog 화면 / Django admin 변경 없음** (Codex v4 finding 2). `normalized_question` 확인은 (a) `python manage.py shell` 조회 또는 (b) DB 직조회로만 한다. BO/admin 노출은 v0.6.x 운영 가시성 후속 이슈로 분리. → `chat/admin.py` 는 본 PR 의 수정 범위에 포함하지 않는다.

### 7.4 history 와의 상호작용
- 다음 turn 의 history 에 들어가는 값은 `raw` (사용자 발화 그대로). rewriter 가 직전 turn 의 raw 를 보고 의미를 보정하는 흐름은 v0.5.1 계약([[v0.5.1 plan]]) 대로 유지.
- 단, rewriter 가 현재 turn 을 다룰 때는 normalized 를 입력으로 받는다 (§7.3).

### 7.5 충돌 우선순위 (최종 결선)
1. **InputNormalize (신규, 본 플랜)** — graph 입구. 텍스트 단위 치환만.
2. **DB RouterRule** — normalized 기준 매치.
3. **DATE_CONDITION 키워드** — normalized 기준 매치.
4. **LLM Router** — normalized + history.
5. **Query Rewriter** — normalized + history.
6. **Retrieval** — rewriter 결과 우선, 없으면 normalized.

이 순서는 v0.5.1 까지의 계약을 깨지 않는다 (1번이 입구에 신설된 것이 유일한 변화).

## 10. 수동 QA 시나리오
사전:
- BO 로그인. RouterRule 충돌 확인 (`경조사` 키워드가 RouterRule 에 이미 있는지 — 있으면 결과 해석에 포함).
- ChatLog dashboard baseline.
- 규칙 0건으로 시작.

### 시나리오 A — 등록한 exact 규칙이 동작 (Codex finding 8: 두 갈래로 분리)
single-shot 은 `chunk_hits` 가 있고 no-info/casual 이 아닐 때만 ChatLog 를 저장하고, agent/workflow 경로는 ChatLog 를 저장하지 않는다. `rudwhtk → 경조사` 가 RouterRule 에 잡혀 agent/workflow 로 빠지면 A-2 의 ChatLog 단언이 깨질 수 있으므로 시나리오를 분리한다.

**사전 공통**: BO `입력 정규화` → 신규 등록: `pattern=rudwhtk`, `replacement=경조사`, `match_type=exact`, `priority=100`, `enabled=ON`.

#### A-1. 라우팅/답변 정규화 확인 (경로 무관)
1. 채팅창에 `rudwhtk` 입력.
2. 기대: 답변 내용이 `경조사` 질문과 동일한 흐름을 탄다.
3. UI 에 표시되는 사용자 발화는 `rudwhtk` 그대로 (raw 보존).
4. ChatLog 저장 여부는 단언하지 않는다 (경로에 따라 달라짐).

#### A-2. ChatLog 저장 단언 (single-shot 자료 기반)
1. 사전: 정규화 결과(`경조사`) 가 **RouterRule / DATE_CONDITION 에 잡히지 않아** single-shot 경로로 가는 케이스를 고른다. (BO RouterRule 목록 확인 후, 충돌하면 임시 disable 또는 다른 pattern 으로 변경.)
2. 입력 후 응답에 자료 청크가 붙어 `chat_log_id` 가 반환되는지 확인.
3. ChatLog row 확인: `question = 'rudwhtk'` (raw), `normalized_question = '경조사'`.
4. ChatLog admin/조회에서 embedding/dedup 키가 normalized 기준으로 잡혔는지(같은 normalized 키의 기존 row 와 cluster 가 합쳐졌는지) 확인.

### 시나리오 B — 미등록 오타는 그대로
1. 규칙에 없는 오타 `dudghkdrnj` 입력.
2. 기대: 정규화 미적용. LLM Router 가 raw(=normalized) 그대로 분류. `normalized_question` 빈 값.

### 시나리오 C — 비활성화 효과
1. 시나리오 A 의 규칙을 토글로 disable.
2. `rudwhtk` 재입력.
3. 기대: 정규화 미적용. 답변 품질이 일반 LLM Router 경로 결과.

### 시나리오 D — contains 과잉 적용 방지
1. `pattern=사`, `match_type=contains` 로 규칙 등록 시도 → form validation 으로 reject 되는지 확인.
2. `pattern=경조`, `replacement=경조사`, `match_type=contains` 는 허용. `경조 한도` 입력 시 `경조사 한도` 로 변환되는지 확인.

### 시나리오 E — exact 우선 + contains 단독 (single best rule)
1. exact: `정산일 → 급여 정산일` (priority=200).
2. contains: `정산 → 정산일` (priority=100).
3. `정산일` 입력 → exact 1건 적용 후 종료. 결과: `급여 정산일`. (contains 가 추가로 걸리지 않아야 함 — `급여 정산일일` 같은 오버랩이 발생하면 회귀)
4. `정산만` 입력 → exact 미매치, contains 1건 적용. 결과: `정산일만`.
5. 같은 입력에 exact 와 contains 가 동시에 후보일 때 exact 만 적용되는지(=`applied` 길이 1) 단언.

### 시나리오 F — 삭제 후 재확인
1. 시나리오 A 규칙 삭제.
2. `rudwhtk` 입력 → 정규화 없음 확인.

### 시나리오 G — DATE_CONDITION 우선순위 무영향
1. `급여 지급일은?` 입력 (정규화 규칙 무관).
2. 기대: 기존대로 DATE_CONDITION 으로 agent 라우팅, LLM Router 미호출.
